## 1. Project Overview

**University Market** (internal codename: **UniTrade**) is a Flutter mobile application that serves as a peer-to-peer campus marketplace. It allows university students to buy, sell, and trade items (textbooks, electronics, clothing, etc.) exclusively within their university community.

- **App Name:** UniTrade
- **Package ID:** `com.example.university_market`
- **Firebase Project:** `university-market-2b9d7`
- **Target Platforms:** Android (primary), iOS, Web
- **Minimum Android SDK:** 23

### Core Features
- Email/password authentication restricted to `@students.edu.jo` university email addresses only
- Email verification required before accessing the marketplace
- Product listings with category filters, course code tagging, and price filters
- Real-time chat between buyers and sellers
- User profiles with rating/review system
- Watchlist (saved listings)

## 3. Architecture Rules

This project uses a **layered architecture** (not full Clean Architecture). The layers are:

```
lib/
├── constants/       # App-wide constants (colors, routes, text styles)
├── data/            # Static/seed data (dummy_categories.dart etc.)
├── models/          # Plain Dart model classes (no business logic)
├── services/        # Firebase service classes (Auth, Firestore operations)
├── providers/       # Riverpod providers (state management layer)
├── screens/         # UI screens organized by feature
│   ├── auth/
│   ├── home/
│   ├── listing/
│   ├── chat/
│   └── profile/
├── widgets/         # Reusable UI components
├── firebase_options.dart   # Auto-generated by FlutterFire CLI — DO NOT EDIT
├── main.dart               # App entry point
└── router.dart             # Named route definitions
```

### Layer Responsibilities

- **`models/`** — Pure Dart data classes with `fromJson` / `toJson`. No Firebase imports.
- **`services/`** — All Firebase SDK calls happen here ONLY. Services are plain Dart classes (not providers themselves).
- **`providers/`** — Riverpod providers expose services and reactive state to the UI.
- **`screens/`** — `ConsumerWidget` or `ConsumerStatefulWidget` only. No direct Firebase calls in screens.
- **`widgets/`** — Stateless or stateful widgets with no Firebase/Riverpod dependencies unless explicitly necessary.
- **`constants/`** — Only `const` values. No logic.

### Strict Rules
- **Never** call `FirebaseFirestore.instance`, `FirebaseAuth.instance`, or any Firebase SDK directly inside a widget or screen. Route through services → providers → UI.
- **Never** put business logic inside model classes.
- **Never** create a new `Provider` inside a screen file. All providers live in `lib/providers/`.
- **Never** use `setState` inside a `ConsumerWidget`. Use `ref.watch` / `ref.read`.

## 5. Coding Standards

### General
- Use `const` constructors wherever possible.
- All public classes, methods, and providers must have a brief doc comment (`///`).
- Prefer named parameters for constructors with more than 2 fields.
- Never use `dynamic` — use explicit types or generics.
- Never use `print()` — use `debugPrint()` or proper error handling.
- Handle all async errors with `try/catch`. Never let exceptions propagate silently.

### Dart/Flutter Specifics
- Use `?? ` (null coalescing) and `?.` (null-aware) — never force-unwrap with `!` without a null check guard.
- Prefer `final` over `var`. Use `var` only for local loop variables where the type is obvious.
- Use `Error.throwWithStackTrace(exception, st)` for rethrowing errors with stack traces (see `user_service.dart` as reference).
- Use `FutureProvider.autoDispose` for data that should refresh when screen is left.
- Use `NotifierProvider` (not `StateNotifierProvider`) for mutable state — this project is on Riverpod v2.

### Naming Conventions
| Kind | Convention | Example |
|------|-----------|---------|
| Files | `snake_case` | `product_service.dart` |
| Classes | `PascalCase` | `ProductService` |
| Providers | `camelCase` + `Provider` suffix | `productListProvider` |
| Methods | `camelCase` | `fetchFilteredListings()` |
| Constants | `camelCase` (in a `class`) | `AppColors.primary` |
| Routes | `camelCase` strings | `AppRoutes.login` |

## 6. UI/UX Rules

- **Color palette:** Always use `AppColors` from `lib/constants/app_colors.dart`. Never hardcode hex values in widgets.
- **Text styles:** Always use `AppTextStyles` from `lib/constants/app_text_styles.dart`. Never hardcode `TextStyle(...)` inline.
- **Named routes:** Always navigate with `Navigator.pushNamed(context, AppRoutes.xxx)`. Never use anonymous routes.
- **Loading states:** Use `shimmer` package for skeleton loading screens. Never show an empty screen while data is loading.
- **Error states:** Always show a user-friendly error message widget. Never show raw exception strings to the user.
- **Images:** Use `flutter_image_compress` before any upload. Display images with a fallback placeholder widget.
- **Theme:** The app uses `Inter` as the primary font family. Do not change this.
- **Responsive:** Layouts must work on screens from 360dp to 428dp width (standard Android phones).

## 7. Firebase Rules

### Authentication
- Only `@students.edu.jo` email addresses are permitted. Validation is in `AuthService.isValidEduEmail()`.
- Email verification is mandatory before a user can post or message. Check `user.emailVerified`.
- The `authStateProvider` (StreamProvider) is the single source of truth for auth state.
- The `isAuthenticatedProvider` returns `true` only when signed in **and** email is verified.

### Firestore Collections
| Collection | Purpose |
|---|---|
| `users/{uid}` | User profile documents |
| `products/{productId}` | Product listing documents |
| `conversations/{convId}` | Chat conversation metadata |
| `conversations/{convId}/messages` | Sub-collection of chat messages |

### Firestore Queries
- Always filter by `status == 'Available'` when fetching public product listings.
- Compound queries (filtering + ordering on different fields) require a Firestore composite index. Create the index before writing the query.
- Use `orderBy('createdAt', descending: true)` as the default sort for listings.
- Range filters (`isLessThanOrEqualTo`, etc.) must be applied on the same field as `orderBy`.

### Security
- The file `firestore.rules` at project root contains Firestore security rules. Any rule changes must be tested before deployment.
- Never expose API keys in committed code beyond what is already in `firebase_options.dart` (which is intentionally included as per FlutterFire CLI convention).
- Never store passwords, tokens, or sensitive data in Firestore documents.
- User documents (`users/{uid}`) must only be writable by the authenticated owner (`request.auth.uid == uid`).

## 12. Project-Specific Gotchas

1. **Riverpod v2 only.** Do not use `StateNotifierProvider`. Use `NotifierProvider` and `AsyncNotifierProvider`.
2. **`FutureProvider.autoDispose`** is used for product listings — they refresh when re-entered.
3. **`isAuthenticatedProvider` checks both sign-in AND email verification.** Do not bypass this.
4. **Compound Firestore queries** that mix range filters with ordering on different fields will throw a runtime error. Always read Firestore's composite index requirements first.
5. **`flutter_image_compress`** requires the image to be a local file path — it does not accept network URLs.
6. **`geolocator`** requires runtime permissions on Android. Always request and check permissions before calling location APIs.
7. **`shimmer`** should only wrap layout-matching placeholder widgets, not arbitrary containers.
